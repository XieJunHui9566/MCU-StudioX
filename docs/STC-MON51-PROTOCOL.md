# IAP15F2K61S2 Monitor V2.5 串口调试协议

本页依据 2026-10-09 当前实板会话和旧项目保存的 STCMON51.DLL 1.19 反汇编整理。实板身份来自用户确认的 IAP15F2K61S2；转接器为 CH340 / COM14，115200、8N1、无流控，监控 hello 返回 V2.5。本页只覆盖该次监控版本，不能自动用于其他 STC 型号或版本。

测试固件为 216 字节 RAM 计数程序，BIN SHA-256 `2DE74703C8FD2BCD3E444F0136C84DFB1F44DC862FD95F95CA2E37ED538C2CB6`。用户已明确允许写入并验证。没有发送监控区写入、芯片配置修改或 ISP 整片擦除命令。产品原生 C# 后端及 IDE 入口已接入；后续源码实板验收只附加已有程序，未重新下载。早期实验脚本不是产品依赖。

## 命令与回复格式

命令为紧凑帧：`FF 5A LEN PAYLOAD CHECKSUM`，`LEN = PAYLOAD 字节数 + 1`，从 FF 到 CHECKSUM 的字节和模 256 为零。当前连接后的命令没有前导 00，也不补零到 65 字节。

数据回复为 `02 DATA CHECKSUM`，全帧字节和模 256 为零。长度由命令上下文决定，回复没有自己的长度字段。版本/控制回复为 `06 00 DATA[4] 04`；这种回复没有同类加法校验和，不能把它标成校验失败。

| 操作 | PAYLOAD | 当前证据 |
| --- | --- | --- |
| hello | `00 00` | `06 00 56 32 2E 35 04`，V2.5 |
| 全寄存器读取 | `00 01` | 19 字节数据回复 |
| 暂停运行 | `00 02` | 持续运行后暂停成功，随后 hello/寄存器读取成功 |
| 设置 PC | `02 00 PC_HI PC_LO 00` | C4/CE/C3 设置后回读对应 PC |
| 返回复位入口 | `02 00 00 00 00` | PC 回读 DBFD，寄存器部分复位；它没有启动执行 |
| 全速运行 | `08 00` | 程序执行至 A5 断点；无断点时持续累计，随后可暂停 |
| 原生指令单步 | `08 01` | 10 次真实指令单步通过，包括 MOV、INC、MOVX、LJMP、LCALL、RET |
| 读内存 | `04 SPACE ADDR_HI ADDR_LO COUNT` | COUNT 字节数据回复 |
| 写 CODE | `02 05 ADDR_HI ADDR_LO COUNT DATA...` | 6 个固件数据块和临时 A5 断点写入/恢复均有读回验证 |
| 监控用户程序擦除 | `06 00 00 00 00` | ACK 约 2.5 秒；原生用户程序下载已用于明确选定的 188 字节构建，完整回读及源码断点通过，不使用普通 ISP |

控制 ACK 的四字节数据常为零，ACK 不证明程序已执行或命中断点。原生单步回复四字节数据的前两字节为新 PC，高字节在前；本次第三字节与新 PC 所在的下一指令操作码一致，第四字节均为零。第三/四字节的完整含义尚未验证，不作为产品能力门禁。

旧客户端的 `GO_PAYLOAD=02 00 00 00 00` 实际是复位入口 PC 操作，导致回读 PC 一直是 DBFD。旧 `identify()` 的 `08 01` 实际执行了单步，不是型号识别，不能用该回复确定料号。

官方驱动反汇编的对应路径：`AG_GoStep → 0x10003649 → 0x1000254A` 发送 `08 00`；单步路径 `0x100035AE → 0x1000246B` 发送 `08 01`；暂停路径 `0x10001EB0` 发送 `00 02`；`0x1000241D` 和 `0x10002F7B` 属于 PC 设置。

## 首次同步与运行中附加

COM18 的冷启动对照确认首次顺序影响连接：原实现先发暂停帧，随后 hello 为零接收；即使之后再省略暂停也没有恢复。重新上电后的第一条操作改为 `80`、`80`、`00 00` 时，直接返回 V2.5，216 字节固件和 DBFD 跳板均匹配。这与旧原厂桥接日志的首次连接顺序一致。单独重写三字节复位向量未解决旧连接顺序的问题；监控 CODE 视图 DC00–F3FF 全为 FF，也不能据此推断物理监控区被擦除。

原生客户端首次连接先同步并 hello；仅在 hello 超时且请求暂停时，才在同一串口参数下发送暂停并再次同步。已成功连接的会话暂停仍先发 `00 02`，异步断点停止后仅同步读取。未知版本、接收错误和调用方取消不触发该超时退路，不扫描波特率或写入配置。修正版在用户确认重新上电后的首次连接、真实断点、指令单步、运行后暂停、结束恢复及运行中重新附加共 14 项通过。[冷启动原始结果](../.artifacts/mon51-com18-diagnostic-20261009/native-synchronize-first-cold/result.json)

## 寄存器回复布局

| 19 字节数据中的偏移 | 含义 | 交叉验证 |
| --- | --- | --- |
| 0 | A | INC A 后由 0 变为 1 |
| 1 | B | 保留原值；与驱动布局对应 |
| 2–9 | 当前寄存器组 R0–R7 | MOV R7,counter 后 R7=1 |
| 10–11 | DPH、DPL | MOV DPTR,#0x0020 后为 00、20 |
| 12–13 | PC，高字节在前 | 与断点地址及每次原生单步回复一致 |
| 14 | PSW | A 从 0 到 1 时奇偶位改变，与驱动寄存器组掩码一致 |
| 15 | SP | LCALL/RET 对应 7→9→7 |
| 16–18 | 标志/状态，完整含义未验证 | 原样保留 |

旧 `parse_registers()` 把 0/1 当状态，把 10/11 当 A/B，并将 SP/PSW 对调。初次实验因此错误判断 INC A 没生效；原始帧已保存，修正后重跑通过。驱动 `0x10002F9F` 的寄存器拷贝及 `ec9d/ec9c` 使用方式与新布局相符。

## 内存空间编号

| SPACE | 空间 | 地址约束与证据 |
| --- | --- | --- |
| 01 | 直接 DATA/SFR | 8 位地址；DATA 0x30 的 counter 已实测，SFR 未逐项验收 |
| 02 | XDATA | total 0x0020–0x0021 的 0→1→3 已实测；本监控布局用户上限 0x03FF |
| 04 | 间接 IDATA | 8 位地址；低 128 字节与 DATA 共享，不能把它当 XDATA |
| 05 | CODE | 固件全部读回匹配，断点恢复后整段代码再次匹配 |

驱动 `0x10002C9C` 读间接 IDATA 使用 04，`0x10002D70` 读直接 DATA/SFR 使用 01，`0x10002E44` 读 XDATA 使用 02，`0x10002EC1` 读 CODE 使用 05。旧 SPACE_XDATA=04 是错误的，会把用户变量显示为另一个 RAM 空间的值。

厂商手册规定监控占 Flash 0xDC00–0xF3FF、XDATA 0x0400–0x06FF；此外，本次 V2.5 实测 DBFD–DBFF 是复位跳板，保存固件的前三个复位向量字节 `02 00 4C`。设置 PC=0 后从该跳板执行能进入完整 SDCC 启动和 main，无需再次断电激活。普通用户代码和软件断点均应避开此跳板；监控需要 P3.0/P3.1。[STC15 官方手册，第 873 页](https://www.stcmicro.com/datasheet/STC15F2K60S2-en.pdf)

## 断点、停止与恢复

本次实际有效的软断点字节为 A5。设置前核对板上代码与选定固件一致，保存原指令字节；写入后读回确认；运行到该地址后核对 PC、变量和栈；最后恢复并读回原字节。旧客户端写入的 FE 是普通 MOV R6,A，不能作为此版本的断点。

运行到断点时收到异步 00/FF 同步字节；持续无断点运行时没有该字节。单个同步字节不具有独立的地址或校验信息，产品后端仍须结合协议状态、停止握手及寄存器 PC 验证停止原因。不得收到控制 ACK 或等待一段时间后就无条件报告 breakpoint。

原生单步 08 01 本身不需要写临时 CODE 断点，已通过两字节 MOV 指令、三字节 MOV DPTR、调用和返回。实验为了在 checkpoint 建立起始位置使用过一次临时 A5；随后 10 条原生单步命令之间没有 CODE 写入。产品实现应优先使用原生单步，减少 Flash 改写，并另行处理源码步过、函数返回、条件断点和多个用户断点的管理。

实验最终恢复所有改写字节，重新核对 216 字节固件 SHA-256 一致，恢复测试程序运行并关闭串口。没有修改旧仓库代码、产品版本号或创建 Git 提交。

## 用户寄存器上下文与 RAM 写入

产品下载入口只接受带构建回执和 CDB 的 IAP15F2K61S2 Mon51 构建，执行前重新核对 HEX/CDB/源码身份；用户 CODE 写块限 40 字节、上限 DBFC，address=0 仅允许单独三字节 LJMP 向量并最后提交。读回包括二进制间隙 FF 和 DBFD–DBFF 跳板，随后设置逻辑 PC=0 并核对 DBFD，默认不 GO。下载失败记录跨会话保留，明确完整重写成功才解除；取消或失败清理不得运行部分固件。擦除 ACK 使用 8 秒独立期限，其余请求保留 2 秒期限。实际工程 188 字节下载、源码断点及单步记录见 [原生应用服务实板验收](../.artifacts/mon51-breakpoint-20261009/hardware-r2/result.json)。

官方驱动通用写路径 `0x100023B6` 发送 `02 SPACE ADDR_HI ADDR_LO COUNT DATA...`，收到控制 ACK。`0x10002D0D` 的间接写使用 SPACE=04；SetRegs 的 `0x10003083` / `0x10003177` 经此路径编辑保存的用户寄存器上下文：A=E0、B=F0、PSW=D0、SP=81、DPL=82、DPH=83。当前寄存器组 Rn 使用 `(PSW & 18h)+n`。不能用 SPACE=01 的物理 SFR 写入代替用户上下文修改。

C# 后端使用此上下文路径，编辑后重新读取 19 字节用户寄存器核对。2026-10-09 已实板验证 A、B、DPTR、R5 编辑并恢复；用户 XDATA 暂存字节和 DATA counter 编辑并恢复。控制 ACK 不单独作为成功证据。内存写 API 限下 128 字节 DATA/IDATA 和 XDATA 0000–03FF；不开放通用 CODE/SFR/上半 IDATA 写入及擦除 API。

源码逐过程/跳出在已核对返回位置使用临时 A5，并核对调用栈 SP，条件/日志断点不满足停止条件时执行原指令再继续。所有类型/行位置来自实际 CDB，指令长度由 C# 8051 解码器确定。原始驱动文件 SHA-256 为 `92F948B98AADCF55FD92FDF20955F5CC9E37EF391F10844388274C2D26C56917`；源码实板记录见 [17 项验收](../.artifacts/stc-mon51-full-hardware-r1/result.json)。
