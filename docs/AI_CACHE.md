# AI 连续对话与 DeepSeek 缓存

## 可实施路线

对齐 DeepSeek Harness 的连续协议设计：常规续聊只追加消息，动态上下文只在变化时追加完整快照；需要整理上下文时集中处理，随后继续追加。产品版本保持 0.2.6.15。

1. 保住请求前缀。保存真实的 user、assistant、tool、reasoning_content 和工具配对；重开对话沿用同一快照。修正只有两条协议消息时丢弃推理字段，以及每次发送只取六轮造成的滑动。
2. 隔离动态上下文。技能目录按名称和作用域排序，变化后在历史末尾追加完整替代快照，清空时明确撤销旧目录。工具定义继续使用已排序的小型固定集合，额外 schema 按需查询；系统与工具契约变化时重新建立兼容快照。
3. 用相同负载验证。离线测试实际 Chat Completions 编码、连续保存/恢复、长工具任务、容量回收和权限边界。线上验收应使用相同模型、思考强度、工具集与任务，分别记录首请求、普通续聊、整理后首请求和中断请求的实际 usage，不用离线前缀比例代替服务端命中率。

## 实现与边界

`AiReplaySnapshot` 以工程、当前系统提示及工具定义的内容指纹隔离协议；只有最新一份快照留在对话文件。GZip 只对本地保存进行无损压缩，HTTP 请求使用解压后的原始消息。快照禁止注入 system/developer 角色，并校验消息顺序、工具配对、解压大小和本地格式版本。

本地最大请求仍为 2 MiB，协议条数上限从 128 调整到 512。活动工具协议高水位为 140,000 字符/224 条，低水位为 64,000 字符/120 条；历史前缀上限为 180,000 字符，并给新任务预留工具批次空间。跨轮整理先回收旧完整工具批次，必要时移除更旧完整对话块并留下明确的历史节选。活动任务的最近工具批次保持完整；任务结束后的续聊边界允许整体回收该批次，保留最终答复与执行记录，避免超大已完成批次阻断续聊。已整理内容需要时重新读取。以上是有界客户端策略，不声称填满模型的百万 token 窗口。

每条对话仍受 512 KiB、256 轮的原存储上限约束。先移除旧的重复快照，再回收旧轮协议和推理副本；极端不可压缩数据或可见问答占满空间时会撤下可选快照并回退旧历史回放。可见问答超限时拒绝覆盖原记录。快照的压缩载荷最多 384 KiB，解压最多 8 MiB。

单个新工具批次可能超过活动协议高水位。此时若总请求逼近 360,000 字符或 512 条的硬边界，会额外集中回收已结束历史，并保留当前技能目录与新批次完整结果；仍放不下才返回原有容量诊断。该回收会引起一次前缀重建。

页面图像仍只进入当次请求，不持久化；图像离开后前缀可能变化。系统提示或工具契约更新、容量整理、旧记录迁移、服务端缓存淘汰以及失败/取消请求都可能导致冷请求。这次改动没有引入新协议、虚构缓存句柄、填充无关文本或放宽工具权限。

## 统计口径与测试

界面“最近一轮缓存”是一次用户发送期间多次模型调用已报告用量的累计；上下文圆环采用最后一次请求的 prompt_tokens。不能把不同请求各自缺失的 hit/miss 拼成一个命中率；缺失字段保留未知。

`tools/StudioX.AiValidation/CacheContinuationChecks.cs` 使用本机 HTTP 处理器和真实请求编码器，覆盖连续十二轮保存/重开、普通回答推理回放、逐消息 JSON 与工具定义一致性、技能变化/删除、容量回收、损坏/越权角色/解压超限拒绝以及部分 usage。既有长工具任务、流式协议、调整方向、MCP 权限与外部服务测试继续执行。

本次基线的连续十二轮测试有 6/11 次完整保留前一次输入前缀，并因普通回答的 reasoning_content 丢失而失败。修复后的相同输入为 11/11；这表示客户端协议保持稳定，不是线上命中率、回答质量或费用节约百分比。原始基线与测试日志保存在 `.artifacts/ai-cache-20261113/`。

最终离线结果：174 项 AI 检查、12 项 Agent/MCP 长任务检查（含单任务 180 次实际本地工具调用）、137 项桌面职责检查和 13 项架构检查通过；40 轮连续对话触发 2 次容量回收。16 个大读取结果与较长既有历史同时存在时，先回收已完成历史并保留全部新结果，结束后可以继续对话。Release 构建零警告、零错误。未调用真实模型 API、未安装替换，版本不变。

全量回归未通过：源代码样式门禁被六处本轮未修改文件阻断，MCP 全量契约检查的 `pic_download` 与既有基线不一致；不改写这些基线掩盖失败。上述专项通过不代表全量门禁通过。最终内容指纹、日志及分项结果见 `.artifacts/ai-cache-20261113/result.json`。

## 官方依据

- [DeepSeek 缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)：前缀单元持久化和匹配，命中按尽力提供，建立与淘汰由服务端负责。
- [DeepSeek 推理与工具调用](https://api-docs.deepseek.com/guides/thinking_mode)：携带 tools 时，所有保留轮次的 reasoning_content 都应回传，包括没有发起工具调用的回答。
- [DeepSeek Harness Agent loop](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md)：连续历史追加、动态上下文快照、系统/工具声明变化与整理对前缀的影响。

核对日期：2026-11-13。只将这些官方机制作为设计依据，不宣称与 DSH 的所有功能或线上结果完全相同。
