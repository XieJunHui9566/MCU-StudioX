# 工程健康检查与修复入口

入口是“工具 → 工程与构建 → 工程健康检查…”或“帮助 → 工程健康检查…”，也能在命令面板搜索。可以检查当前工程，或选择尚未成功打开的 StudioX 工程目录。IDE 原生编译、下载前的构建和调试前的构建会先调用快速检查；具体错误阻止本次构建并打开健康页，注意项允许继续。MCP/CLI 的底层构建仍使用原有严格工具及工程校验。

## 两档检查

快速检查只读取工程清单、器件身份、根与必要生成 CMake、编译参数、当前版本的工具清单及入口、工具锁定、原生 SDK 入口和已有缓存。不会遍历全部 SDK 文件，不执行 CMake、idf.py、用户代码或探针。入口存在单独标为说明，明确没有校验文件内容。构建时仍完整核验工具内容。

深度工具检查重新完整校验当前工程所需开发环境组件，随后仅运行已校验工具的固定 `--version`，检查 GCC/SDCC、CMake、Ninja、Python、Git 能否启动。每个进程限时 15 秒，保留退出码、超时、输出截断状态及原始输出。大型 SDK 会较慢，顶部停止按钮可取消；取消不留下可用的半成品报告。启动检查通过不保证 ABI、SDK Python 依赖或固件编译成功。

MicroPython 不被要求安装原生 GCC；Zephyr 的实验支持不被当作已开放固件构建。系统环境只记录被隔离的变量名称，不导出变量值，也不修改系统 PATH。

## 修复动作

每项提供对应处理入口和帮助：工具问题定位到明确 ID/版本的开发环境组件行；参数问题进入工程编译设置；构建入口问题打开根 CMake；ESP 配置问题进入模组与配置页。没有在编辑器打开的工程需要先打开，才允许进入其编译/ESP 设置，避免改到另一个工程。

“预览并重建配置缓存”先列出将移动的生成文件及大小。确认后移动固定范围：`.build` 下的 CMakeCache、CMakeFiles、CMake File API、Ninja 构建文件、编译数据库、IDF 环境身份和旧构建凭据。保留源码、SDK、全部 sdkconfig、工具锁、固件和原始日志。备份保存在 `.build/.studiox-cache-backups/<时间-唯一编号>`，重新编译前没有旧下载凭据。此动作不自动重新配置或编译；下一次用户构建重新生成。

缓存修复与构建共用排他锁。预览后缓存目录或文件元数据变化则拒绝执行；路径越界、重解析点、正在构建、活动调试、取消、清单伪造都不能直接移走文件。移动失败或取消会按相反顺序回退，回退异常完整保留。备份不自动清理，也不提供绕过工程锁定的功能。

## 诊断与验证

原故障页保留完整诊断并新增“检查工程并打开修复入口”，缓存错误有直接入口。报告可以导出本机 JSON，包含检查时间（UTC）、明确工程/目标、模式、所有检查及原始异常，不自动上传。工程切换清除旧结果，新的检查开始时清除旧操作与导出状态。

`tools/StudioX.ProjectHealthValidation` 使用隔离工程和工具验证健康检查与缓存事务；第二参数提供已安装 Ninja，仅用于离线 `--version` 夹具。可选的真实工程及 runtime 参数只做快速检查并核对原文件哈希。

`MCU StudioX.exe --preview-project-health <新输出目录> <ESP-IDF工程>` 使用隔离用户数据，读取实际工程、测试自动构建拦截和故障入口、深浅主题、窄窗口、取消后的状态及项目切换，保存截图与 `health-ui-result.json`。不会连接设备或编译固件。
