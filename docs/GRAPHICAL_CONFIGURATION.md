# MCU 图形化配置契约 v1

状态：设计草案，2026-10-21。本文及配套 Schema 是完整 v1 的契约基线。2026-10-22 的 [STC 试行插件](../plugins/StudioX.StcConfigurator/README.md)已接入可选模板/工程关联、来源绑定、通用图形视图与单配置文件保存；使用独立 `mcuConfigurationPreview` 能力。完整提供者协议、生成计划及多文件保存尚未实现，不能将试行能力标为完整 v1。产品版本、StudioX Pack 格式 1 和工程格式 1 保持不变。

本文的“必须”“不得”是契约要求，“建议”允许实现给出有理由的替代。基础文件结构由 [JSON Schema](contracts/mcuconfig-v1.schema.json)约束；跨字段引用、来源、芯片电气规则和文件事务还必须满足本文及[插件契约](GRAPHICAL_CONFIGURATION_PLUGIN.md)，不能仅凭 Schema 通过宣称配置有效。

首版试行插件现增加[准确工程范围与时钟托管](GRAPHICAL_CONFIGURATION_CLOCK.md)：仅匹配工程显示功能入口，由配置文件统一管理下载源频率与分频后编译时钟。该有限扩展不等于完整 v1 提供者协议。

## 1. 目的和职责

图形化配置是可选的系列/厂商插件能力。用户不安装插件，也可以从正常模板创建工程，手写初始化代码、编辑、构建、下载和调试；这些操作继续遵守原有支持范围与授权。

器件包模板提供特殊文件 `device.mcuconfig` 的初始内容。创建工程后，工程根目录的同名副本同时承载准确器件资料和用户配置，其作用类似工程的图形化配置源文件。它随源码进入版本管理，不保存本机插件安装路径、账号、设备连接授权、编辑器布局或主题。

| 所有者 | 负责内容 |
| --- | --- |
| 器件包作者 | 已核对型号/封装、引脚和复用、外设、时钟关系、来源证据、初始配置及匹配的普通源码模板 |
| 图形化插件 | 明确支持的器件组合、配置规则、参数说明、冲突判断、频率计算、代码生成和显式迁移方案 |
| Packages / Engine | 包内文件校验、根据准确选择复制初始文件、记录来源绑定；保持原有构建职责 |
| Application | 插件选择、快照与取消、配置编辑、修改计划校验、预览、应用、保存和恢复 |
| Desktop / PortableDesktop | 呈现经校验的数据、接收输入；不求解芯片规则、不执行插件 UI 程序集 |

芯片差异和 SDK API 不能写成通用图形控件中的型号分支。插件在独立进程执行；进程隔离不等于权限沙箱，沿用现有插件信任与授权要求。

## 2. 范围

v1 为每个工程定义至多一份主配置，绑定一个准确 MCU 型号、一个封装、一个模板和一个框架/SDK 组合。多 MCU 工程、任意原理图、PCB 布线及从手写 C/C++ 反向恢复配置不属于 v1。

v1 包含封装/引脚、外设实例及其参数、时钟节点与关系、配置验证、生成计划和版本迁移计划。DMA、NVIC、复用组、电源域等系列规则可以由版本化 profile 数据表达，但没有实现和验证的功能不得出现在支持声明中。

本文件不替换 `.studiox/project.json`、工具锁、现有下载/调试配置、CubeMX `.ioc`、AG32 `.ve` 或其它专用源文件。v1 首批仅面向明确声明本契约的器件包原生 C/C++ 模板。现有 AG32、CubeMX、ESP-IDF、Arduino、Zephyr、PIC 和 MicroPython 流程不会自动迁移；适配其它工程类型须单独确定生成文件与构建归属。

## 3. 文件和模板关联

### 3.1 编码与命名

- 扩展名为 `.mcuconfig`，默认目标名为工程根目录 `device.mcuconfig`；文件内容为 UTF-8 JSON，不带 BOM，建议 LF 和两空格缩进。
- `format` 固定为 `studiox.mcuconfig`，`formatVersion` 固定为 `1`；JSON 属性名及标识符区分大小写。
- 拒绝重复属性、无效 Unicode、注释、尾逗号、非有限数值和超过深度/容量限制的内容。不要用宽松 JSON 编辑器的解析行为作为格式标准。
- 不允许通过文件指定可执行脚本、XAML、程序集、网络 Schema 或初始化时必须访问的 URL。来源 URL 仅作为证据文字，不自动访问。
- 未知公共字段必须拒绝图形编辑和生成，原文保留、普通文本查看仍可用。扩展数据仅放在本契约指定的 `profileData` 或 `parameters` 对象，由准确 profile 校验，不静默丢弃。

### 3.2 拟增加的模板字段

在准确器件的模板项中增加可选字段：

```json
{
  "graphicalConfiguration": {
    "file": "templates/hal/device.mcuconfig"
  }
}
```

`file` 是包内相对路径，指向 `documentKind: "template"` 的普通文件，受完整文件索引、SHA-256、路径、链接和容量校验。该字段不复用目前只允许 `src/`、`include/` 的 `template.files`，也不放宽它们的目标路径。

共享模板时，不同器件项可以引用不同初始配置文件；同一文件只能被目标身份、封装、profile 和初始配置完全相同的组合复用。v1 不支持在文件内插入占位符、运行模板脚本、根据相近料号或本机 SDK 猜测资料。大型共享源数据可以在包制作时生成准确文件，不能留到工程打开时猜测。

旧模板省略该字段，行为保持不变。增加字段仍是 Pack 格式 1 的待实现可选扩展；旧程序可能忽略未知字段，不能声称旧程序会完整识别或必然拒绝该能力。因此普通模板源码必须在没有图形插件、没有复制该文件时仍能独立创建和构建。

### 3.3 拟增加的工程字段

```json
{
  "graphicalConfiguration": {
    "path": "device.mcuconfig"
  }
}
```

`path` 由工程根目录解析，v1 固定为 `device.mcuconfig`。该字段只负责明确关联，不重复保存引脚、时钟或用户参数。没有关联的同扩展名文件可以作为文本查看；不能仅靠扩展名扫描结果自动绑定或生成代码。

工程创建必须在既有 staging 内完成所有校验、绑定和写入，成功后再发布工程。声明了初始文件却缺失、损坏或目标不符时，创建失败并保留诊断，不创建缺失配置的半成品。插件缺失不影响该步骤，也不在创建时启动或自动安装插件。

## 4. 文档结构

根对象的全部字段如下，除明确允许 `null` 的字段外均为必填：

| 字段 | 含义 |
| --- | --- |
| `format` / `formatVersion` | 文件种类与公共格式版本 |
| `documentKind` | `template` 或 `project` |
| `target` | `vendorId`、准确 `deviceId`、准确 `packageId`、架构标识 |
| `profile` | 配置规则/profile、数据 Schema、插件/提供者及框架/SDK 身份 |
| `origin` | 模板中为 `null`；工程中由核心写入来源绑定 |
| `definitions` | 器件基础资料快照，图形编辑时只读 |
| `configuration` | 模板内为初始选择；工程内为用户当前配置 |
| `generation` | 模板及尚未生成的工程为 `null`；生成后记录实际生成器与输出凭据 |

完整结构样例见 [虚构模板](contracts/examples/demo.template.mcuconfig)和[虚构工程](contracts/examples/demo.project.mcuconfig)。样例仅使用不存在的演示器件，不可作为真实 MCU 包或电气参数使用。

### 4.1 target 与 profile

`target` 必须与所选器件项和 `definitions.package.id` 一致。`architecture` 是无推断的原始架构标识，不用于自动选择构建器或下载入口。

`profile` 包含：

- `id`、`version`：配置规则/数据模型的准确身份，不能仅用厂商名代替。
- `pluginId`、`providerId`：预期插件和其配置提供者，不能用任意同系列插件自动替换。
- `dataSchema: { id, version, sha256 }`：profile 扩展数据的准确本地 Schema 身份，SHA-256 针对 Schema 文件原始字节。Schema 由受信任插件提供，必须匹配该身份；其结构与 Schema 方言由该 profile 版本固定。不得联网解析引用。
- `framework: { id, version }` 及 `sdk: { id, version } | null`：生成代码采用的准确框架与 SDK 组合。`sdk: null` 只表示该 profile 明确不需要 SDK；不表示自动寻找 SDK。版本不使用范围、`latest` 或空字符串。

公共 Schema 接受的结构只说明数据可读。profile 数据 Schema 在公共校验后校验同一个完整文档，以便按资源 ID、功能和目标组合分别约束全部 `profileData`、`parameters`、单位及可选值。它不得覆盖公共约束，也不得将扩展点解释成任意执行代码。缺少参数的未完成配置可由 Schema 接受，再由插件报告阻断错误；没有匹配 profile 时状态为“规则不可用”，不能显示“配置有效”。

### 4.2 definitions：器件基础资料

| 字段 | 内容与约束 |
| --- | --- |
| `package` | `id`、名称、封装种类、物理引脚数量及示意图宽高；不是开发板型号 |
| `pins[]` | 稳定物理 `id`、封装位置 `position`、显示名、类别、示意坐标、允许功能和证据引用 |
| `peripherals[]` | 稳定外设实例 ID、类别、名称、信号列表、证据引用及 profile 数据 |
| `clockTree.nodes[]` | 稳定节点 ID、类别、名称、允许输入 ID、示意坐标、证据引用及 profile 数据 |
| `evidence[]` | 来源 ID、标题、版本、URL/文献位置、源文档 SHA-256 以及页码/章节定位 |
| `profileData` | 由 profile 定义的其它只读资源、依赖与规则参数 |

物理引脚 ID 在当前 profile 的同一目标中稳定，不以可改显示名或数组下标作为身份。`position` 必须唯一；GPIO 名不能代替物理位置。电源、地、复位、晶振、保留和 NC 引脚也需准确记录，`pinCount` 必须等于完整物理引脚清单长度。引脚坐标须位于封装示意宽高范围内；示意图坐标不是实际封装尺寸或 PCB 焊盘坐标。`synthetic` 证据仅允许结构样例或测试夹具，不得用于真实器件包的发布或真实工程的生成。

引脚功能 ID 在所属引脚内唯一；关联外设和信号必须存在。无外设关联的功能，其 `peripheralId` 和 `signalId` 同时为 `null`。同名逻辑信号跨引脚的可用性不表示能够同时分配；复用、重映射、电气与资源冲突由 profile 判断。

时钟节点 `kind` 为 `source`、`mux`、`pll`、`divider`、`gate` 或 `output`。允许输入 ID 必须引用当前图中的其它节点，不得自引用。静态关系图不被强制假定为 DAG；启用后的实际依赖不能出现无法求解的循环。PLL、倍/分频、总线和 Flash 等限制必须来自证据与 profile，不写入通用绘图代码。

目标及基础资料在图形编辑中只读。更改型号、封装、profile、框架、SDK 或任何基础资料均通过迁移计划进行，不以普通参数编辑替代。

### 4.3 configuration：用户选择

| 字段 | 数据 |
| --- | --- |
| `pins[]` | `{ pinId, functionId, label, parameters }`，可选 `locked` 默认为 `false`；每个物理引脚至多一条选择 |
| `peripherals[]` | `{ peripheralId, enabled, parameters }`；每个外设至多一条 |
| `clocks[]` | `{ nodeId, enabled, inputId, parameters }`；每个时钟节点至多一条 |
| `profileData` | 当前 profile 定义的跨实例资源配置及其它用户参数 |

未出现的引脚表示用户未作分配，不等于芯片寄存器复位值；未出现的外设/时钟表示没有启用请求，也不能据此宣称实板处于禁用状态。参数缺失表示未设置；不得默默用 UI 默认值、其它芯片资料或 SDK 默认值补齐。默认参数必须明确写入模板初始配置或经预览加入用户配置。

`label` 为用户命名，不改变引脚 ID。`locked` 保护功能分配，外设自动换脚也须遵守；用户解除锁定后才能改配或释放，不表示硬件寄存器锁。`parameters` 的类型、范围、枚举、单位及允许缺失项由准确 profile Schema 定义。以 Hz 为单位的频率不得保存为含糊的 `8` 或自由格式 `8 MHz`；精确计算使用整数或 profile 定义的有理数。频率计算结果属于派生数据，不作为另一个可编辑事实来源。

未分配、未完成甚至存在冲突的中间配置允许保存；图形界面必须持续显示诊断，禁止在有阻断错误时生成代码。模板默认配置须与随附普通源码的初始行为一致，并通过对应规则校验；用户后续修改可以处于未完成状态。结构非法、重复字段或未知公共语义只能保留原文为文本，不能伪装成成功保存的结构化编辑。

### 4.4 origin：模板到工程的绑定

模板必须使用 `origin: null`、`generation: null`。创建工程时核心将 `documentKind` 改为 `project`，并注入：

```text
packId, packVersion, packContentHash, deviceId, templateId,
templateFile, templateSha256, definitionsSha256
```

包内容哈希沿用现有 `PackRepository` 算法；`templateSha256` 对应包内初始文件原始字节；`definitionsSha256` 对应本节定义的基础资料规范化摘要。`origin.deviceId`、`target.deviceId`、工程 Manifest 中器件必须一致，其它包与模板身份同样逐项核对。

包内初始文件不得填写其所在包的最终内容哈希或自身最终文件哈希；这些值由已校验的包索引与仓库结果注入，避免循环哈希。包作者不能通过模板内容伪造工程绑定。

基础资料完整快照保存在工程文件中，不要求重新安装包才能查看。生成时还需核对工程保留的器件资料、来源凭据与 SDK 身份；来源不足时明确报错，不自动下载或换包。哈希只能证明完整性，不证明厂商来源真实或作者身份。

## 5. 版本、摘要与来源

### 5.1 版本分离

公共文件 `formatVersion`、profile 版本、profile 数据 Schema、插件版本、SDK 版本、器件包版本和产品版本各自独立。同一 profile ID/版本不得替换数据 Schema 或改变参数含义；破坏语义的修改必须使用新 profile 版本，公共结构的破坏性变更需要新格式版本。

未知文件格式、profile 或控件版本不可自动降级。新插件只有明确声明支持原准确组合时才能编辑旧文件；新版本生成器与上一轮不同，必须在生成预览中显示变化。插件缺失、停用或版本不匹配时保留原文件和生成源码，已有源码的普通构建继续沿用原流程。

### 5.2 摘要算法

所有摘要为小写 64 位十六进制 SHA-256。原始文件摘要对文件字节计算，不做换行或编码转换。

结构化摘要采用 [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785)规范化后的 UTF-8 字节，不是缩进序列化，也不是按当前 .NET 默认 JSON 输出直接计算。实现仍使用独立 C# 核心，不引入 Node 或浏览器运行时。

- `definitionsSha256 = SHA256(JCS(definitions))`，创建时记录到 `origin`；普通编辑不得改变它。
- 生成输入投影恰好包含根对象中的 `format`、`formatVersion`、`documentKind`、`target`、`profile`、`origin`、`definitions`、`configuration`，以原字段名组成一个对象。
- `inputSha256 = SHA256(JCS(生成输入投影))`。排除 `generation`，避免记录自引用；UI 布局和临时校验结果也不进入文件。
- 空白和对象属性顺序不影响结构化摘要；数组顺序仍参与摘要。普通写入保留数组顺序，不以“格式整理”重排。
- 所有 JSON 数值必须可表示为有限 IEEE 754 binary64；整数限于 `[-9007199254740991, 9007199254740991]`。需要更大整数或更高精度时，profile 必须使用明确约束的十进制字符串或整数分子/分母，禁止依赖解析器的隐式舍入。

JCS 摘要用于语义过期判断；生成预览和文件写入前还必须比较原始文件 SHA-256、编辑缓冲区版本及工程代次，防止覆盖内容或格式上的外部修改。

### 5.3 generation：生成凭据

非空时必须含 `generator`、`inputSha256`、`outputs`。`generator` 记录实际 `pluginId`、插件准确版本、插件内容指纹和 `providerId`；内容指纹沿用插件安装/启用所用的准确内容身份。

`outputs` 按路径列出插件拥有的生成源码，每项含项目相对 `path` 与对应字节 `sha256`。这些文件允许用户查看和编辑；与凭据不符时显示“生成源码已修改”，重新生成必须作为冲突处理。文件中不得嵌入对其最终自身摘要的依赖。

凭据描述最近一次完整保存成功的生成结果。单纯修改或保存配置不能更新它。`inputSha256` 与当前输入不符时标为“配置未生成”；输出缺失或摘要不同标为“输出已变化”；插件不可用另行标记，不能混写成配置无效。

## 6. 图形编辑和生成生命周期

1. 打开工程：核心只读取、识别和核对文件；插件启动遵守既有启用流程，不因文件存在而执行未受信任代码。
2. 编辑配置：插件提出候选配置，核心验证只允许修改 `configuration`，一次用户操作形成一次撤销记录。不修改源文件，不连接设备。
3. 规则求值：返回诊断、可选项和频率等派生状态，绑定文档版本、语义摘要及工程代次。插件迟到结果不得恢复旧状态。
4. 保存配置：允许保存未完成配置，保持旧生成凭据；原始磁盘基线变化时保留内存和冲突。
5. 请求生成：基于当前内存快照、相关源文件与构建配置快照生成完整计划。计划必须覆盖新增/替换/移除的全部生成源码、构建登记及配置凭据更新。
6. 预览与应用：用户明确应用，核心重新核对计划前提，所有变更一起进入未保存缓冲区/新文件暂存。拒绝或过期时不应用任何一项。
7. 保存生成结果：通过独立的“保存生成结果”操作执行有恢复记录的多文件事务。直到全部输出、构建登记和配置凭据保存成功，才能记录 `generation` 成功。不能把若干独立文件保存宣称为磁盘原子事务。
8. 实际构建：继续使用原构建后端与工具锁，验证输出。生成成功、编译成功和实板验证是三个独立结论。

“应用”后的生成凭据只是待保存状态。部分文件被普通保存、IDE 异常退出或磁盘写入失败时，必须保留恢复记录和原始诊断，状态为“保存未完成”；重启提供明确恢复/回退选择，不自动重生成，也不宣称生成成功。插件退出不能丢失已应用的内存配置和源码。

没有插件时普通构建不启动配置生成器。若宿主支持该契约，应显示配置与源码不同步状态；用户仍可明确选择按现有源码构建，构建记录标明这一状态。下载和调试继续使用实际源码/固件凭据，不把图形文件当作烧录授权或已生成证据。

## 7. 源码和构建归属

v1 默认生成范围为 `src/generated/mcuconfig/` 与 `include/generated/mcuconfig/`，明确记录每份受管文件。用户业务代码放在其它文件，通过公开初始化入口调用；v1 不支持任意 C/C++ 中的用户代码区合并或反向解析。

- 首次生成遇到已存在但未被上一份凭据拥有的目标文件，按冲突处理，不能接管或覆盖。
- 后续生成只能替换/移除上一份凭据拥有且当前字节摘要未变的文件。用户修改过时停止整个计划，展示差异；用户可自行迁移代码、另存或放弃本次计划，不能静默覆盖。
- 缩小配置导致不再需要的旧输出必须显式列为删除操作；不能留下旧初始化代码继续参与编译，也不能删除其它文件。
- 根 `CMakeLists.txt` 的源码登记为独立修改项，沿用已有归属、字面量、脏缓冲区、只读和一次撤销检查。复杂配置无法证明安全修改时，保留诊断和手动操作说明，不应用部分计划。
- `src/main.c` 的初始化调用由模板预先提供稳定接入点。模板必须提供位于生成目录之外的初始实现和明确的生成后衔接方式，首次生成不能依赖覆盖模板中未归生成器拥有的占位文件；具体机制由准确 profile/模板约定，并验证生成前后均可链接。没有接入点的已有工程必须经明确迁移计划接入，禁止搜索任意 `main()` 后盲目插入。
- 不通过生成修改 `.studiox/project.json`、工具锁、下载/调试设置、`device/` 内部配置、SDK、插件或外部目录。目标/框架变化使用单独的迁移流程。

生成过程不得下载 SDK、搜索全局 PATH 或隐式运行外部工具。需要厂商生成器的后续适配必须先定义额外工具组件契约及独立执行计划，不能把命令行或脚本塞进本文件。

## 8. 显式迁移

升级包、profile、SDK、封装、型号或公共格式均不在打开/构建时自动进行。迁移必须提出来源与目标身份、每项配置的映射、无法迁移项、资源冲突、预计源码与构建修改及可恢复的原文件备份。

只改变显示名不应改变稳定资源 ID。无法证明等价的引脚、通道或时钟关系必须标为未映射，不能按同名或数字相近自动承接。迁移后配置重新求值，旧生成结果标为过期；新源码须另行生成。迁移计划也不能授予下载、解锁或设备连接权限。

## 9. 通用校验和限制

校验按四层执行并明确区分失败来源：

1. 宿主结构校验：编码、重复字段、公共 Schema、路径、容量、稳定 ID、引用、唯一性与身份一致性。
2. profile Schema 校验：全部扩展字段、参数类型、单位和未知参数。
3. 插件语义校验：引脚占用、复用组、时钟范围、共享资源、SDK 支持及依赖组合。
4. 实际构建及独立硬件验收：分别记录准确目标、版本、范围及原始证据。

限制为独立上限，不保证达到某一个上限时仍能达到其它上限：

| 项目 | v1 上限 |
| --- | --- |
| 文件原始字节 | 512 KiB |
| 文档 JCS 规范化字节 | 256 KiB |
| JSON 嵌套深度 | 32 层 |
| 物理引脚 / 单引脚功能 | 512 / 32 |
| 外设 / 单外设信号 | 256 / 64 |
| 时钟节点 / 单节点允许输入 | 512 / 32 |
| 证据项 / 单项引用列表 | 128 / 32 |
| 生成源码文件 | 128，总原始 UTF-8 内容 128 KiB |
| 一次完整生成计划 | 编码后单条协议消息同时不超过 1 MiB 字符与 1 MiB UTF-8 字节 |

宿主和插件写出协议时应保留合法 Unicode 字符，避免无意义的全字符转义；发送前仍按实际包络校验上限。超过限制明确报错，不截断文件、分批写入计划或静默省略引脚。v1 未定义分片协议；更大数据需要后续显式能力协商。

所有项目/包内路径遵守现有 `PathBoundary`：相对路径、正斜线、无 `..`、绝对路径、链接或 Windows 保留名，按 Windows 大小写不敏感规则拒绝目标冲突。Schema 的路径正则只做初筛，不能替代实际边界与祖先链接检查。

## 10. 诊断分类

| 代码 | 含义 |
| --- | --- |
| `MCUCONFIG_FORMAT` / `MCUCONFIG_LIMIT` | 格式、未知公共字段或容量不合法 |
| `MCUCONFIG_TARGET` / `MCUCONFIG_ORIGIN` | 目标/封装或来源绑定不一致 |
| `MCUCONFIG_DEFINITION` | 基础资料摘要、唯一性、引用或来源有误 |
| `MCUCONFIG_PROVIDER` / `MCUCONFIG_PROFILE` | 匹配插件不可用或不支持准确 profile/Schema |
| `MCUCONFIG_RULE` | 插件发现资源冲突、不完整参数或其它阻断规则 |
| `MCUCONFIG_STALE` | 工程、文档或文件前提已变化 |
| `MCUCONFIG_OUTPUT_CONFLICT` | 输出未归生成器所有、已修改、只读或路径冲突 |
| `MCUCONFIG_BUILD_REGISTRATION` | 不能安全登记构建源码 |
| `MCUCONFIG_SAVE_INCOMPLETE` | 多文件保存未完成，等待明确恢复 |

规则诊断保留插件原始代码、信息、证据引用和来源，宿主分类代码不能吞掉原始异常。没有插件或生成过期是状态，不自动变成芯片配置错误。

## 11. 后续实现的验收要求

- 不安装插件，旧模板与新模板的普通创建/编辑/构建均可用；不生成或启动任何硬件操作。
- 包文件与项目文件分别通过 Schema；错型号/封装、来源、自引用哈希、重复 ID/属性、坏引用、大小写路径和链接输入拒绝。
- 模板能在不启动插件的情况下准确实例化，初始配置无隐含默认；包升级不改变已有工程快照。
- 明确验证 JCS 官方向量、属性顺序与空白等价、数组顺序不等价、数值边界，以及来源和生成摘要投影。
- 插件能力缺失、错误 profile、Schema 被替换、不同 SDK/框架、迟到响应、取消、切换工程、禁用和崩溃均不覆盖用户数据。
- 图形视图与表单在 WPF/便携端遵守同一数据语义，未知控件拒绝，大小与缩放不改变配置事实。
- 生成新增/替换/移除、源码登记、一次撤销、脏缓冲区、外部修改、过期预览、只读和取消覆盖真实场景。
- 多文件保存逐阶段注入故障/进程退出，证明没有虚假的成功凭据，恢复和回退保留用户已有改动。
- 选定真实系列后，对实际覆盖的每种 profile/SDK/代表型号生成并真实编译；不能把虚构 Schema 样例或软件编译宣称为实板验收。

首批试行范围已明确为 IAP15L2K61S2 / LQFP44 / SDCC，来源和准确能力见试行插件说明；它不覆盖本节完整验收要求。其它系列仍须补充独立厂商资料、支持矩阵、电气规则和实际生成编译证据。
