# STC8H8K64U 原生 USB 下载

器件包 `stc.stc8/0.1.8` 添加 STC8H8K64U。使用 CMake + Ninja + SDCC，链接代码区 65024 B，512 B EEPROM 单独保留为容量边界；内部 RAM 256 B、XRAM 8192 B，专用 USB RAM 1280 B 不作为普通 XRAM 链接。容量依据[厂商页面](https://stcmicro.com/cn/stc/stc8h8k64u.html)和 stcgal 的 F784 型号表。

下载按钮旁的设置入口打开独立“STC 下载配置”页，选择串口 ISP 或原生 USB。串口仍使用保存的 COM 和波特率。USB 使用内置 C# 协议和 Windows HID，点击下载后动态等待器件；用户手动进入硬件 USB ISP 并插入电脑，无需固定端口。多个待下载设备出现时停止，不随机烧录。

当前工厂协议核对范围为 VID 34BF / PID 1001、型号码 F784、ISP 7.4.12U。其它 Boot ROM 不在擦写资格内。FF0F 下载桥和 FF01 用户自制引导程序均不复用此通道。与官方工具同时运行时拒绝打开；单设备和工程构建租约贯穿会话。

USB 当前支持保留本次实机的时钟/选项，或内部 RC 24 MHz。24 MHz 使用本次状态表的校准槽，不复制样板固定 trim。硬件选项新增下文所列的 10 项；其它频率、外部时钟和未核对的配置位暂未开放。选项包与实机分区在擦除前检查；配置结束应答确认后才发送退出。显示成功不代表 Flash 读回或程序运行已验证，协议不提供原程序备份。

Windows 每个 HID 报告 65 B：报告 ID 00 + 64 B 负载。长命令连续分段；实际官方工具首写命令 32、续写 12，跳过全 FF 页。接收包核对长度、方向、结束标志、加和校验与命令应答，禁止将进度 100% 当作最终成功。

协议证据：2026-10-31 用户操作 AiCube-ISP v6.97C 的单块、跨空白页多块、24 MHz 三轮被动监听。观察器本身没有发送；纯报文夹具位于 `tools/StudioX.StcIspValidation/fixtures/stc8h-usb.json`，含原始记录哈希。`--usb <runtime> <pack> <new-output>` 执行实际 CMake/SDCC 编译与注入 HID 的离线回放；`--preview-stc-usb` 检查真实 WPF 设置界面。离线通过不等于 StudioX 实板下载验收。

包生成：`New-Stc8UsbPack.py` 基于哈希锁定的 0.1.6 包，先补充标准整数头，再添加准确型号并发布为 0.1.8，保留所有旧型号、Mon51 和 RT51 资源。使用 CLI `pack` 生成 StudioX 格式 1 索引，不能手工复用旧 `files.sha256.json`。

### USB 布局：已确认与不能直接套用的部分

对已经记录的 54 字节身份 payload `S`，以及 45 字节配置命令 payload `C`，均从第 0 字节开始计数，且不含 Windows report ID 和传输帧头：

| 配置字段 | C 偏移 | 证据 |
| --- | --- | --- |
| 配置命令和前导 | 0–4 | `04 00 00 5A A5` |
| 固定前段 | 5–28 | 三轮官方样本相同；没有授权把这些保留位置作为新增开关 |
| 用户 IRC 频率 | 29–32 | 大端 Hz，24 MHz 样本为 `01 6E 36 00` |
| 校准参数 / 分频 | 33–35 | 使用本次芯片参数，不固定复制参考程序的 trim |
| 原始选项区 | 36–44 | 三轮样本均逐字节等于 `S[8:17]`，当前记录为 `FF FF FF FF 3E BF AF F7 FE` |

串口参考 `initialize_options()` 取 `S[9:12] + S[15:17]`，其 `build_options()` 把 M0 放在 40 字节 body 的 32，M1–M4 放在 36–39。但将同一规则盲套到 USB 记录，得出的 M 为 `FF FF FF F7 FE`，而实际 USB body 在这些发送位置的值为 `FF BF AF F7 FE`。这已经证明二者不能直接拼接复用；尚不能据此判断哪个串口固件布局有错。

将 USB 尾部连续的 `3E BF AF F7 FE` 当成同一五字节语义，能得到另一组看似合理的复位/低压/下载条件，但它仍是**待验证假设**，不能显示成实机读回值或据此开放写入。当前正确边界仍是整体保留原始区，再对每个明确选项做官方单变量对照。

### 三个需要先解决的接入问题

1. **USB 频率能力分开建模。** 手册明确的 16 个预置 MHz 值为：5.5296、6、11.0592、12、18.432、20、22.1184、24、27、30、33.1776、35、36.864、40、44.2368、48。当前 IDE 仅核对保留/24 MHz，通用设置上限 40 MHz、STC8G/H 串口能力上限 36 MHz 都不能用于完整 USB 列表。扩展时还须逐频率确认本芯片校准槽、分频及工作条件，不能只放开文本框或套用第三方程序的固定 trim。
2. **EEPROM 大小必须进入工程契约。** 65024 B 代码 / 512 B EEPROM 是当前锁定 profile 的划分，不是物理 Flash 的永久属性。手册说明可配置 EEPROM 从 Flash 尾部向前安排，且物理区可能仍可执行代码。以 64 KiB Flash 的 8 位目标、独占 EEPROM 区的工程策略为例，保留 8 KiB 数据后，应把代码上限同步约束到 57344 B，不能仍允许镜像到 65024 B。IAP 逻辑地址与 MOVC 物理地址须分开；MCS-251 目标不能套用该公式。当前 USB 下载尚未独立解析/匹配此分区，不应宣称支持任意分区下的数据保留。
3. **擦除策略需要独立证据。** 新选项写入通常在代码擦除/写入之后；因此本次写入“下次擦除 EEPROM”不能被表述为已控制之前的擦除。串口参考另有擦除范围参数，且源码明确提醒实际效果仍不完全确定；目前 USB 只抓到 `03 00 00 5A A5`。必须通过准确 ROM 的选项变化及带已知数据的 EEPROM 对照，核对本次/下次行为后再承诺保留数据。

### 后续抓包清单与实现顺序

本次没有自动启动监听。下一轮准备时固定型号、Boot ROM、同一小程序、IRC 24 MHz、全部其它选项和主机版本，记录每项改动前状态、唯一 UI 改动、擦除命令、配置命令、ACK、下一次检测结果。最后一次检测只验证字段是否持久化，不把它称作 Flash 读回；功能效果还需相应实板测试。
