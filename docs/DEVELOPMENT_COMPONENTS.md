# 开发环境组件与开发环境组件归档

目标是完整安装包和轻量安装包共用同一套组件身份、导入、修复和升级管理。完整包预装当前全部开发环境组件，轻量包按工程需要安装开发环境组件；两种安装包保留相同 IDE 功能、器件包和内置插件。

## 第一步已实现

- `DevelopmentComponentIdentity` 使用现有 `toolset.json` 的 ID、组件版本、主机平台和编译器身份。唯一安装键为 ID/版本/平台，当前仅支持 Windows x64；文件名不参与识别。
- 新归档使用 `.mcutoolchain`，默认以 7z/LZMA2 压缩。格式 1 仅含文件条目，根目录保存原始 `toolset.json`，其 `sha256` 索引全部其余文件。清单和文件直接复制，不重新序列化、不更改原始清单指纹。按文件签名兼容既有 ZIP/Deflate 的 `.mcutoolchain` 和 `.studioxtools`。
- 原有 `.studioxtools` 是相同格式的明确兼容入口。导入、导出、离线修复、工程工具准备和分发下载支持两种扩展名。新导出默认 `.mcutoolchain`，旧分发目录保留原缓存路径及续传片段。
- 菜单“工具 → 开发环境组件 → 导入开发环境组件…”及“开发环境组件管理”的导入按钮共用应用服务，两种发行配置均包含入口。
- 新版本并存安装。相同 ID、版本和平台已有不同清单指纹时拒绝覆盖；相同内容重复导入会完整校验归档和安装目录，成功后跳过安装，不修改任何已安装文件。
- 缺失、损坏、重复条目、目录条目、链接、越界路径、不支持的主机平台或格式均不视为组件就绪。修复仍为独立操作并保留可回滚目录。
- 导入不执行归档中的程序，不修改工程、工具内容锁、sdkconfig 或系统 PATH；它也不构成固件或硬件验收。

组件包版本沿用现有 `ToolsetManifest.Version`，内部版本由 `ComponentVersions` 记录。第一步没有重新编号已发布组件或解除 ESP-IDF 等框架的 SDK 版本校验，已有工程锁继续生效。

## 本地打包

```powershell
./tools/New-McuToolchain.ps1 -ToolsetDirectory <已验证开发环境组件目录> -OutputFile <新文件.mcutoolchain>
```

打包脚本核对原清单文件集合和逐文件 SHA-256，不修改开发环境组件。`New-DistributionCatalog.ps1` 可登记该归档；工具清单上限与导入器一致为 32 MiB，允许大型 SDK 的完整文件索引。目录的来源、许可证、更新说明和发布者签名独立管理，SHA-256 不证明发布者身份。打包不等于确认再分发许可，私有厂商授权文件禁止进入归档。

## 第二步已实现：器件包需求与工程内容锁

器件和模板都可声明 `developmentComponents`，每项是精确的 `id/version/compilerId/host/purpose`。器件层必须包含与现有主工具字段相同的组件，模板层增加组件；相同身份去重，相同 ID 的不同版本、平台或编译器被拒绝。不接受 `latest` 或版本范围。当前上限 64 个组件，仅支持 `win-x64`；用途是说明文字，不是可执行命令。

```json
{
  "developmentComponents": [
    {
      "id": "arm.gnu",
      "version": "1.0.0",
      "compilerId": "arm-gnu-15.2.rel1",
      "host": "win-x64",
      "purpose": "工程编译"
    }
  ]
}
```

以上仅展示字段结构；`compilerId` 必须与实际组件的原始 `toolset.json` 一致，不能照抄示例替代实际身份。未声明新字段的格式 1 包沿用原有三个明确工具字段，不改写已发布归档或其版本。MicroPython 脚本模板不继承原生构建需求，不允许另外声明原生组件。

新建页面展示所选模板需求。创建工程不要求组件已安装，生成工程把选择结果保存到 `.studiox/project.json`；准备工程开发环境组件、健康检查、开发环境组件管理与构建使用共同的需求解析。工程的快照与带显式声明的 `device/manifest.json` 必须一致；删去快照中的额外需求不能绕过器件包要求。AG32 引脚/逻辑功能沿用其明确配置，并纳入共同检查。RTL 仿真仍按单独配置准备组件。

完整哈希校验通过后，首次构建建立 `.studiox/development-components.lock.json`，为每项需求记录 ID、版本、平台、编译器和清单指纹；原 `toolchain.lock.json` 继续保留并交叉核对。缺少或内容不符时在生成器/编译器启动前失败，不自动下载、不删除锁。构建全程持有每个组件的使用租约。安装新版本不改变需求或内容锁。已安装包的所有模板、已登记/最近/当前工程及已有锁参与旧版保留检查。

快速入口仅检查有限元数据及入口文件，不递归扫描 SDK，也不启动工具。准备导入的预览绑定工程和器件清单、内容锁，变化后需重新预览；完整校验仍在构建或手动深度检查执行。当前未解除 IDF SDK/profile 的精确版本约束，也未加入组件升级后的工程迁移。

## 第三步已实现：完整与轻量发行

`Publish.ps1` 共用自包含桌面、语言服务、Git、器件包、内置插件及独立宿主的发布流程。`full` 预装当前全部开发工具；`light` 不含 `runtime/toolsets`、`runtime/hdl` 或 `runtime/stc-isp`。`Publish-Light.ps1` 提供直接入口，旧 `base` 参数与 `Publish-Base.ps1` 明确转到 light，不再使用裁掉器件包和插件的独立实现。

两种发行记录 `release.json` 的配置及 `development-components.json` 的预装组件身份和原始清单指纹。安装器共用 AppId、版本和安装位置；完整版文件名保持原名，轻量版使用 `Light-Setup.exe`。已有组件目录，包括损坏或不完整版本，整目录保留；安装器只补入不存在的预装版本，不合并文件或修复组件。组件修复、使用占用和删除仍走 IDE 的工具管理。

卸载保留预装、后来导入和旧安装器曾拥有的开发工具，并保留用户数据与工程。旧卸载记录的处理及程序旧文件的保留边界见 [安装说明](INSTALLER.md)。本地安装测试使用唯一测试身份和微型工具文件，另用真实完整/轻量 Payload 检查共同内容和轻量页面；安装测试不执行微型工具或访问硬件。

## 第七步：升级验证副本

分发页增加“创建升级验证副本…”。先保存当前编辑内容，明确选择已安装的同一器件包 ID、同一器件及模板的另一个版本，选择全新副本目录并显示预览。普通原生 Pack 工程使用公共应用服务；不依赖 WPF 或 STC 型号。第七步当时尚未支持 IDF 及带逻辑/引脚生成配置的工程，第八步已接入对应策略；CubeMX、MicroPython 和 Zephyr 仍须专用迁移流程。

预览完整核验原器件包和目标包，比较架构及内存布局；核对原工程的器件支持文件、生成配置、用户源码和内容锁。器件支持目录的修改、缺失或新增文件都会阻止自动替换，提示人工审阅。输入、包或锁在预览后变化时拒绝创建。新目录不能已存在、位于原工程内部、是原工程的父目录或落入器件包；源和目标路径的父目录不能有 junction/符号链接。

副本重新生成目标器件支持，复制原工程用户文件、根 CMake 配置、编译设置和 STC 时钟配置。不复制旧开发环境组件锁、构建缓存、Git 历史或调试会话；构建服务完整校验目标组件后建立副本自己的新锁。服务只编译副本，不连接硬件，不修改原工程或原组件；失败与取消保留已创建的副本和 `.studiox/component-migration-result.json`，原始诊断不丢失。采用副本前还需要检查应用行为；返回原工程即可继续原版本，无需反向改写工程。

迁移校验复用了第六步明确匹配的 STC 新包：保留编辑过的应用源码、CMake 宏、优化和时钟设置完成真实编译；逐文件比较原工程未变。边界包括预览后编辑、SDK 修改、占用目录、嵌套/祖先路径、父目录 junction、取消与刻意的 C 编译失败。验证材料保存到 `artifacts/development-components-step7-20261003`。实际验证范围是 STC 软件编译，不能把通用服务实现表述为其它框架或实板已验收。

产品版本仍为 0.2.5.4B；没有制作正式新安装包或替换当前安装。主 IDE 仓库本轮未提交或推送，独立组件仓库按用户要求单独公开。

## 第八步：ARM、ESP、RISC-V 和 AGM

ARM GNU、WCH RISC-V、xPack RISC-V、AGM AgRV/引脚映射/逻辑工具、ESP-IDF 与 ESP8266 RTOS SDK 均使用共同的 `.mcutoolchain` 导入、精确身份、并存版本和工程内容锁。完整与轻量发行共用管理入口。新组件不会重写已安装的旧组件或原工程需求；使用升级验证副本仍须先导入明确匹配的新器件包。

迁移预览补充 CPU/ABI 参数与保留应用区布局的核对；不能把变更后的 CPU、SDK target 或映射模式当成自动升级。用户源码中的 `src/build` 等目录照常复制，只跳过明确的工程根构建缓存、Git 历史和厂商逻辑缓存。原工程的器件支持与系统生成文件经过基准及生成收据核对，手动改动会阻止自动替换。新目录发布遇到 Windows 文件扫描器的暂时占用时，仅在目标仍不存在且原暂存目录完好的条件下有限重试，不覆盖已有目录。

### ESP 的组件版本和 SDK 版本

开发环境组件修订与 SDK 发行分别管理。例如测试组件 `espressif.idf/1.0.1` 内部仍为 IDF 5.5.4；器件包和工程同时明确这两个身份。构建核对组件用途、内部版本、受索引的 `version.txt` 和目标芯片支持，不允许仅改清单把一个 SDK 冒充另一个发行。语言服务元数据、快速健康检查及 Core Dump 环境使用相同的身份区分；打开工程不新增 SDK 全量扫描。

第八步当时的 IDF 适配仅覆盖明确的 5.x 身份及实际验收的 5.5.4；第九步扩展为明确的 5.x/6.x 身份，仍拒绝 `latest`、版本范围和 7.x。元数据结构支持不代表所有发行或芯片已经通过实际构建，验收需查看具体版本和用例记录。ESP8266 使用独立 RTOS SDK 3.4.0，不能换成 IDF target。不同 SDK 的工具及 Python 依赖需随经过验证的组件提供，不自动下载 SDK。

ESP 升级副本保留原生源码/组件、用户 CMake、`sdkconfig`、`sdkconfig.defaults`、依赖锁和模块配置；配置输入另存于 `.studiox/migration-inputs/`。SDK 可能更新副本的 Kconfig 输出，应用 API 迁移仍需人工处理。原工程配置与内容锁不变。

新建 ESP 副本目录建议使用 ASCII 名称，不含空格或分号；原工程名称含中文时入口自动给出可用的 ASCII 子目录名称。已有父目录可使用实际可用的短路径，新目录尚无短名称，预览在复制和工具校验前拦截不支持的路径。无需搬移原工程或修改磁盘的短名称设置。

### AGM 的多组件构建

AgRV 编译器、VE 引脚映射和原生逻辑工具分别读取器件包声明的组件版本。迁移保留引脚、命名、时钟、模拟配置、Verilog、约束以及逻辑/仿真设置；副本重新生成系统支持并构建。旧版组合逻辑指纹在只读检查时核对映射和逻辑两部分，新构建写入各自的精确内容锁；冲突不能绕过。

## 第十步：7z 开发环境组件容器

- 制作脚本默认使用真实 7z/LZMA2，保持 `.mcutoolchain` 文件名。发布制作通过 `-SevenZipPath` 指定本机 7-Zip；不改变系统 PATH。清单单独压缩，负载使用 64 MiB 固实块和 32 MiB 字典，仅列入索引内的普通文件。原生完整性检查通过后才发布临时输出。
- IDE 使用固定版本 SharpCompress 0.50.3 托管读写器；完整版和轻量版均包含，无需用户另外安装 7-Zip。IDE 导出每文件独立 LZMA2 压缩，方便读取清单。两种压缩策略的组件身份与内容锁相同。
- 预览、导入、重复导入校验、离线修复和工程兼容性预览共用签名识别和边界检查。固实包顺序解压，逐文件比对实际展开长度，全部 SHA-256 验证通过后才替换目录；取消和失败清理暂存副本，保留原组件。
- 最多 200,000 个文件、总展开大小 40 GiB、清单 32 MiB。第三方解码前先检查压缩头和展开头各不超过 64 MiB、解码字典不超过 64 MiB、文件/数据流数量不超限；7z profile 使用 Copy/LZMA/LZMA2，可选固定大小的分支或 Delta 过滤器，无外部属性流。拒绝加密、分卷、自解压、目录、删除条目、大小写冲突、文件与父目录冲突、链接、危险路径及未索引内容。压缩格式变化不改变组件版本、SDK 版本、原清单指纹或工程内容锁。

## P0：组件事务和中断恢复

离线安装和同版本修复沿用已校验副本。发布之前将格式 1 记录写入工具根目录 `.transactions/<事务号>.json`，刷新到磁盘后才移动目录；暂存位于 `.repair-<事务号>/<ID>/<版本>`，原组件位于 `.rollback-<事务号>/<ID>/<版本>`。记录只存精确身份与清单指纹，目录相对于当前工具根解析，安装目录整体移动后仍可恢复。

“开发环境组件管理 → 恢复未完成操作…”先只读查看记录、目录存在性及有限清单，不因打开页面扫描 SDK、启动工具或替换目录。用户明确操作后取得目标独占维护租约、重新完整校验候选、核对预览未变，再继续发布、确认就位、保留原目录或恢复原组件。目录冲突、无效记录、内容指纹不符和工具占用保留原始诊断及文件。修复未结束的版本不能同时禁用、删除或再次修复；工程准备明确提示恢复入口。已完成记录进入 `.transactions/history`，原备份保留。

恢复不更改工程、组件版本锁或启用状态，也不选择其他已安装版本。完整校验 API 必须持有对应目录的独占维护租约，不能用共享租约或其他版本租约绕过占用保护。下载进度只在数据落盘后报告；同大小缓存也在使用前完整校验，不能以长度判断完整性。该机制验证的是进程终止及文件损坏边界，不声明物理断电或磁盘故障验收。
